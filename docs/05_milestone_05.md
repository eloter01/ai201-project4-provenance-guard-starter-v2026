# Milestone 5 Plan — Write the Labels and the Appeal Path

## Goal

`POST /submit` will map the combined score to one of three reader-facing
labels and record the same guess and label in the audit log. `POST /appeal`
will move a recorded submission to `under_review`, return the existing
confirmation on an exact retry, and record rejected requests.

## Out of scope

- Automatic rescoring, review decisions, or changes to the Milestone 4
  combining rule.
- New authentication, rate limiting, and the full three-trial acceptance
  evaluation.
- Cleanup of existing Ruff findings.

## Steps

After each step, run `python -m ruff check .`,
`python -m ruff format --check .`, and `python -m pytest -q`. Compare both
Ruff results with the existing baseline and include each test with its code.
Review one change per turn and commit only after the user says `commit it`.

1. **Define the labels and score ranges.** Implement `score_to_label` in
   `scoring.py`. Start with `0.35` and `0.65`, using the corresponding
   high-confidence label at either exact cutoff. Align `label_ranges()`,
   the comments in `config.py`, and **Label Variants** in `README.md` with
   the same boundaries.

   | Guess | Score range | Proposed reader-facing text |
   | --- | --- | --- |
   | `human` | `0 ≤ score ≤ 0.35` | This text looks likely to have been written by a person. |
   | `unsure` | `0.35 < score < 0.65` | We’re unsure whether this text was written by a person or generated by AI. |
   | `ai` | `0.65 ≤ score ≤ 1` | This text looks likely to have been generated by AI. You can submit an appeal to request a review. |

   **Tests in `tests/test_scoring.py`**

   - `test_score_to_label_covers_endpoints_and_cutoffs` checks `0`, `1`, and
     values immediately below, at, and above each cutoff.
   - `test_score_to_label_returns_reader_facing_text` checks all three
     messages.
   - `test_label_ranges_matches_mapper` checks the displayed boundaries.
   - `test_score_to_label_rejects_invalid_scores` covers nulls, strings,
     booleans, nonfinite values, and scores outside 0–1.

   **Commit** `feat(scoring): map scores to reader-facing labels`

2. **Use the final label in `/submit`.** In `app.py`, call `score_to_label`
   with the combined `confidence`. Return the resulting `guess` and `label`
   and write the same pair to the decision record.

   **Tests in `tests/test_submit.py`**

   - `test_submit_labels_from_combined_score` covers all three outcomes,
     including a high model score with an `unsure` combined result.
   - `test_submit_audit_matches_response_label` verifies the guess and label
     for the same `content_id`.
   - Re-run the existing submission and rejection tests.

   **Commit** `feat(submit): return and audit the final label`

3. **Make exact appeal retries safe.** In `audit.py`, reuse the existing
   appeal entry when `content_id` and reasoning both match. Hold the audit
   lock across the lookup and append so concurrent retries in the local
   service produce one entry. Different reasoning can be recorded as a new
   appeal for the same submission.

   **Tests in `tests/test_audit.py`**

   - `test_log_appeal_reuses_exact_match` checks that an exact retry returns
     the first entry and adds no row.
   - `test_log_appeal_records_different_reasoning` checks that new reasoning
     is recorded as a separate entry for the same submission.
   - `test_log_appeal_distinguishes_content_ids` checks that the same
     reasoning can be recorded for different submissions.
   - `test_log_appeal_deduplicates_concurrent_retries` checks that simultaneous
     retries produce one appeal entry.

   **Commit** `feat(audit): deduplicate exact appeal retries`

4. **Implement `/appeal`.** In `app.py`, require a JSON object with nonblank
   `content_id` and `reasoning` strings. Look up the original `decided` record
   and use its creator ID. After recording or finding the appeal, return
   `200` with the content ID and `under_review`. Return JSON `400` for
   malformed input and JSON `404` for an unknown content ID, with a rejection
   entry for either case. Surface audit failures as JSON `500`.

   **Tests in `tests/test_appeal.py`**

   - `test_appeal_preserves_original_decision` checks an earlier decision
     record and the appended appeal.
   - `test_appeal_exact_retry_returns_same_confirmation` verifies a single
     appeal entry.
   - `test_appeal_rejects_and_audits_invalid_input` covers malformed and
     non-object JSON plus missing, null, wrong-type, empty, and blank fields.
   - `test_appeal_audits_unknown_id_and_still_returns_404_on_retry` verifies
     that a rejection does not make an ID eligible for appeal.
   - `test_appeal_returns_error_on_audit_failure` verifies JSON `500`.

   **Commit** `feat(appeal): record reviews and rejected requests`

5. **Capture the live sample run.** Record the actual submission, appeal,
   and `/log` requests and responses under **Sample Run** in `README.md`.
   Retain the matching entries in `logs/audit.jsonl`.

   **Manual checks**

   - _All three labels reachable_ verifies each label with real submitted
     text.
   - _Appeal history matches response_ verifies the original decision, the
     `under_review` confirmation, and the single appeal entry after an exact
     retry.

   **Commit** `docs(readme): record label coverage and appeal sample run`

## Final step

Use `curl.exe` against the running service to submit real passages that
reach `human`, `unsure`, and `ai`. Appeal one returned content ID, repeat the
exact request, and verify that both confirmations say `under_review` while
`/log` shows the original decision followed by one appeal entry. Send a
malformed appeal and an appeal for an unknown ID, then verify their `400`
and `404` responses and corresponding rejection entries.

## Risks

- The Milestone 4 agreement rule may make high-confidence AI hard to reach
  with the available samples. If a label is missing, inspect both signal
  scores before revisiting the cutoffs. An AI cutoff change affects both
  the combining rule and the label mapper.
- Retry deduplication relies on the local service's process lock. A
  multi-process deployment would need shared coordination for the same
  guarantee.
